# 05 · K3s, explained from an OpenShift background

## What K3s is

A **CNCF-certified Kubernetes distribution in a single ~70 MB binary** (by SUSE/Rancher).
The API is the same Kubernetes API you know from OpenShift. What's different is how much is bundled and how small it is.

| Piece | OpenShift | K3s (default) | In our install |
|---|---|---|---|
| Container runtime | CRI-O | containerd (embedded) | same |
| CNI | OVN-Kubernetes | **Flannel** (VXLAN) | same |
| NetworkPolicy | OVN | **kube-router** policy controller (embedded) | used by the optional policy |
| DNS | CoreDNS | CoreDNS | same |
| Ingress | OpenShift Router (HAProxy) | **Traefik** | **disabled**: nothing published |
| LoadBalancer | MetalLB / cloud | **ServiceLB (Klipper)** | **disabled**: nothing published |
| Storage | ODF / CSI | **local-path-provisioner** | used by Postgres |
| Datastore | etcd | **SQLite** (single server) or embedded etcd (HA) | SQLite (1 node) |
| Operators | OLM | none (you bring Helm/manifests) | Helm for CNPG |
| Security defaults | SCCs, OAuth | standard K8s RBAC + PSA | + secrets encryption + audit log |

**Why K3s here:**
- It's real Kubernetes, up in ~30 seconds.
- Minimal footprint on one VM.
- The same install works on-prem and **air-gapped** at customer sites (very relevant for government customers).

**Why not GKE:**
- It's managed and good at scale.
- But it adds GCP surface and permissions, takes longer to create, and doesn't transfer to the customer's own hardware.

## How the install works (`scripts/k3s-install.sh`)

1. Reads `k3s-version` and the VM's IP from the **metadata server**.
2. Writes **`/etc/rancher/k3s/config.yaml`**. Every key is a CLI flag, and the file survives upgrades:
   ```yaml
   node-ip: 10.10.1.10
   tls-san: [10.10.1.10]          # API server certificate valid for the IP the bastion uses
   write-kubeconfig-mode: "0600"  # admin kubeconfig readable by root only
   disable: [traefik, servicelb]  # no way to publish anything by accident
   secrets-encryption: true       # Secrets encrypted at rest (AES-CBC key on the node)
   kube-apiserver-arg:            # audit log of every API call
     - audit-log-path=/var/lib/rancher/k3s/server/logs/audit.log
     - audit-policy-file=/etc/rancher/k3s/audit-policy.yaml
     ...
   ```
3. Waits until HTTPS egress works. **Cloud NAT** can take a minute after creation.
4. Downloads `get.k3s.io` and runs it with `INSTALL_K3S_VERSION=v1.35.7+k3s1`.
   - The installer downloads the binary from GitHub releases and **verifies its SHA-256**.
   - It creates the `k3s` systemd service.
5. Waits for the node to be `Ready`.

**Where things are on the node:**

| Path | What |
|---|---|
| `/etc/rancher/k3s/k3s.yaml` | admin kubeconfig (server `https://127.0.0.1:6443`) |
| `/var/lib/rancher/k3s/server/` | datastore, TLS, tokens, audit log |
| `/var/lib/rancher/k3s/storage/` | **local-path volumes = Postgres data** |
| `journalctl -u k3s` | K3s logs |
| `k3s kubectl`, `k3s crictl` | bundled kubectl and container CLI |

## Kubeconfig on the bastion (`20-bootstrap-bastion.sh`)

The file on the node says `server: https://127.0.0.1:6443`. That's useless from another machine.
We stream it **node → laptop pipe → bastion**, rewriting the server to `https://10.10.1.10:6443`.
- TLS still validates because `10.10.1.10` is in the API certificate's SAN (`tls-san`).
- The file is mode 600 on the bastion. It is **cluster-admin**, used for deployment only.
- The validator gets its own 8-hour, namespace-scoped token (`40-validator-kubeconfig.sh`).

Common error: `x509: certificate is valid for 127.0.0.1, ..., not 10.10.1.10` → the `tls-san` line is missing. Fix the config and run `sudo systemctl restart k3s`.

## Ports

| Port | Who uses it | Open from the bastion? |
|---|---|---|
| 6443/tcp | Kubernetes API | **yes** (firewall rule) |
| 22/tcp | SSH | **yes** |
| 10250/tcp | kubelet API (exec, logs, port-forward) | no (API server → kubelet is local) |
| 8472/udp | Flannel VXLAN between nodes | phase 2 (node ↔ node only) |
| 2379-2380/tcp | embedded etcd (HA) | phase 2 (server ↔ server only) |
| 5432/tcp | Postgres **inside the pod network** | **never** |

## Troubleshooting ladder (on the node: `ssh -F .local/ssh_config airis-k3s`)

```bash
sudo journalctl -u google-startup-scripts.service --no-pager | tail -50   # did the install run?
sudo systemctl status k3s
sudo journalctl -u k3s --no-pager | tail -100
sudo k3s kubectl get nodes -o wide
sudo k3s kubectl get pods -A                     # coredns, local-path-provisioner, metrics-server
sudo k3s crictl ps -a                            # containers even if the API is down
curl -sS https://get.k3s.io >/dev/null && echo egress-ok   # NAT / egress firewall
sudo k3s check-config                            # kernel features
```

| Symptom | Likely cause |
|---|---|
| Startup log: `waiting for egress via Cloud NAT` forever | NAT missing, or the egress firewall too strict |
| `k3s.service` fails right away | Bad key in `config.yaml` (YAML indentation!) or bad audit policy path |
| Node `NotReady` | CNI not up yet (wait 30s), or disk pressure |
| Pods `ImagePullBackOff` | No egress, wrong image tag, registry rate limit |

## Phase 2: from one node to HA

- **Servers:** 3 servers with `--cluster-init` (embedded etcd), spread across `me-west1-a/b/c`. They tolerate 1 server loss.
- **Joining:** extra servers or agents join with the token from `/var/lib/rancher/k3s/server/node-token` and `K3S_URL=https://<first>:6443`.
- **Firewall:** add node ↔ node rules for 8472/udp, 10250/tcp and 2379-2380/tcp. Optionally put an internal load balancer in front of 6443.
- **Upgrades:** the system-upgrade-controller (plans) or a rolling update, one node at a time.
- **Air-gapped (likely at government customers):**
  - put `k3s-airgap-images-amd64.tar.zst` in `/var/lib/rancher/k3s/agent/images/`;
  - put the binary in `/usr/local/bin`;
  - install with `INSTALL_K3S_SKIP_DOWNLOAD=true`;
  - use a private registry mirror via `/etc/rancher/k3s/registries.yaml`.
